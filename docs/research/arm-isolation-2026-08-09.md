# Ablation-arm isolation for hooks, rules, and skills

Research for [issue #4](https://github.com/TheRealBillSiegler/claude-plugins/issues/4). Question: a controlled ablation study must run matched Claude Code sessions WITH and WITHOUT a component that is a user-level PreToolUse hook, a user-level rules file (`~/.claude/rules/*.md`), or a skill. What is the sharpest viable per-arm isolation mechanism?

Method: primary sources only — code.claude.com/docs pages, fetched directly, quoted verbatim where the claim is load-bearing — plus direct reads of the local ablation skill's asset files. One GitHub issue is cited for a known footgun; it is flagged as secondary (repo issue tracker, not docs). Every claim below is either quoted-and-cited or marked UNVERIFIED.

## 1. Does `CLAUDE_CONFIG_DIR` redirect the entire user config for a headless `claude -p` run?

Yes, for the disk-backed part of it. Primary source, quoted verbatim from `code.claude.com/docs/en/claude-directory`: "On Windows, `~/.claude` resolves to `%USERPROFILE%\.claude`. If you set [`CLAUDE_CONFIG_DIR`](https://code.claude.com/docs/en/env-vars), every `~/.claude` path on this page lives under that directory instead." That page's file tree covers CLAUDE.md, settings.json, hooks, skills, commands, subagents, workflows, rules, and auto memory — so the redirect is total for everything Claude Code reads from `~/.claude`, not just settings.json.

Caveat verified via the Agent SDK docs (`code.claude.com/docs/en/agent-sdk/claude-code-features`, "What settingSources does not control" table): the global `~/.claude.json` file (distinct from the `~/.claude/` directory) is "Always read" regardless of `settingSources`, and the documented way "To disable" it is "Relocate with `CLAUDE_CONFIG_DIR` in `env`" — confirming `CLAUDE_CONFIG_DIR` also relocates that file, not only the `~/.claude/` tree.

Also from that same table: managed policy settings (org-deployed, OS-level paths such as `/etc/claude-code/CLAUDE.md` or Windows' `C:\Program Files\ClaudeCode\CLAUDE.md`, per `code.claude.com/docs/en/memory`) are read "regardless of this option" and cannot be disabled from the SDK or, by extension, by `CLAUDE_CONFIG_DIR`. For a matched-arms design this is not a confound — managed policy is identical across both arms on the same machine, so it's a constant that cancels out of the delta, not a source of bias.

I did not find `CLAUDE_CONFIG_DIR` documented on `code.claude.com/docs/en/env-vars` itself — I searched that page directly by exact string and it returned zero matches, and a follow-up search asking the fetch tool to enumerate the first 20 env-var names on the page did not surface it either. The `claude-directory` page links to `/docs/en/env-vars` as if the variable is defined there, but the anchor target could not be confirmed; treat the env-vars page cross-reference as UNVERIFIED (possibly a stale doc link) while the substantive claim (what the variable does) is confirmed from `claude-directory` and corroborated from the Agent SDK page.

Known footgun (secondary source — GitHub issue, not docs): [`anthropics/claude-code#37570`](https://github.com/anthropics/claude-code/issues/37570) reports that on Linux/Windows, if `CLAUDE_CONFIG_DIR` is set to a `~`-prefixed path (e.g. `~/.claude-personal`), Claude Code does not expand the tilde and instead treats it as a literal directory name relative to the current working directory, writing credentials to `<CWD>/~/.claude-personal/.credentials.json`. Recipe implication: always set `CLAUDE_CONFIG_DIR` to a fully-expanded absolute path, never a `~`-prefixed one, when building arm directories.

## 2. Does `--settings <file>` merge with or replace user settings? Does it touch rules/skills?

Merges at the key level, not the file level. Primary source, `code.claude.com/docs/en/cli-reference`, `--settings` flag description, quoted verbatim: "Path to a settings JSON file or an inline JSON string. Values you set here override the same keys in your `settings.json` files for this session. Keys you omit keep their file-based values." So `--settings` is a fifth settings *scope* that sits above Local in the precedence order, not a full replacement of the settings tree.

Precedence order, quoted verbatim from `code.claude.com/docs/en/settings` ("How scopes interact" section, which the page's own text treats as equivalent to "Settings precedence"): "1. Managed (highest)... 2. Command line arguments: temporary session overrides 3. Local: overrides project and user settings 4. Project: overrides user settings 5. User (lowest): applies when nothing else specifies the setting."

Exception that matters for hooks specifically: that same page states permission rules "merge across scopes rather than override." Separately, `code.claude.com/docs/en/hooks` states, quoted verbatim: "Hook entries merge across settings levels rather than replacing each other: user, project, and local settings add their own hooks without removing managed ones." This is a second, hook-specific exception to plain key-level override, and it is NOT the same statement as the `--settings`-flag description above. The docs do not explicitly reconcile the two: it is unclear whether a `hooks` key supplied via `--settings` (a "command line arguments" scope) *replaces* the `hooks.PreToolUse` array from `~/.claude/settings.json`, or *adds to* it the same way user/project/local settings add to each other. I asked the fetch tool to locate primary text resolving this directly and it could not find one. **UNVERIFIED — treat `--settings` as unreliable for suppressing a specific real hook entry until confirmed empirically** (e.g., with the `InstructionsLoaded`/hook-listing behavior in `/hooks`, per `code.claude.com/docs/en/memory`'s troubleshooting section, or by checking `system/init`'s session metadata in `--output-format json`).

Does `--settings` touch rules/skills? Indirectly, through specific keys, not through a rules/skills-specific flag:
- `skillOverrides` is a plain settings key (`code.claude.com/docs/en/skills`, "Override skill visibility from settings") and per the general `--settings` semantics should be independently settable per session (`"off"` hides a named skill entirely from Claude, quoted: "Hidden / Hidden" in the visibility table).
- `claudeMdExcludes` is a plain settings key (`code.claude.com/docs/en/memory`, "Exclude specific CLAUDE.md files") that excludes files "by path or glob pattern," matched "against absolute file paths using glob syntax," and is documented as configurable "at any settings layer: user, project, local, or managed policy." The docs demonstrate it only against a project rules directory example (`"/home/user/monorepo/other-team/.claude/rules/**"`); nothing in the mechanism description scopes it to project files only, so applying it to a `~/.claude/rules/*.md` path is a reasonable inference but **UNVERIFIED against a user-scope example** — confirm empirically before relying on it.
- There is no analogous per-hook-entry exclude key documented anywhere I found (`disableAllHooks` is global; `allowManagedHooksOnly` is a different lockdown; neither targets one hook).

## 3. Per-session flags to disable hooks, skills, or specific config elements

Confirmed settings/flags, each quoted from primary source:

| Mechanism | Scope | Source |
|---|---|---|
| `"disableAllHooks": true` | All hooks, globally, everywhere it's set | `code.claude.com/docs/en/settings` |
| `"allowManagedHooksOnly": true` | "Only managed hooks, SDK hooks, and hooks from plugins force-enabled in managed settings `enabledPlugins` are loaded. User, project, and all other plugin hooks are blocked." | `code.claude.com/docs/en/settings` |
| `"disableBundledSkills": true` | Disables every bundled skill except `/doctor`; "Skills from plugins, `.claude/skills/`, and `.claude/commands/` are unaffected." | `code.claude.com/docs/en/settings`, `code.claude.com/docs/en/skills` |
| `"skillOverrides": {"<name>": "off"}` | Hides one named personal/project skill entirely from Claude (not plugin skills — "Plugin skills are not affected by `skillOverrides`") | `code.claude.com/docs/en/skills` |
| `disable-model-invocation: true` (skill frontmatter) | Removes that one skill's description from context entirely, so Claude can't auto-invoke it; you still can via `/name` | `code.claude.com/docs/en/skills` |
| Deny rule `Skill(name *)` in `/permissions` | Blocks Claude from invoking a named skill via the Skill tool | `code.claude.com/docs/en/skills` |
| `"claudeMdExcludes": [...]` | Excludes CLAUDE.md/rules files by absolute-path glob | `code.claude.com/docs/en/memory` |
| `--setting-sources user,project,local` (comma-separated subset) | Loads only the named scopes; excluding `project` skips project rules ("Project rules are skipped if you exclude `project` from `--setting-sources`") | `code.claude.com/docs/en/cli-reference`, `code.claude.com/docs/en/memory` |
| `--disable-slash-commands` | "Disable all skills and commands for this session" | `code.claude.com/docs/en/cli-reference` |
| `--safe-mode` | Disables CLAUDE.md, skills, plugins, hooks, MCP servers, custom commands/agents, output styles, workflows, custom themes/keybindings, statusline/file-suggestion commands, LSP servers, and auto-memory — everything at once, for troubleshooting. Managed-policy hooks/statusline/file-suggestion still apply; managed plugins/skills/CLAUDE.md/MCP do not load. | `code.claude.com/docs/en/cli-reference` |
| `--bare` | "skip auto-discovery of hooks, skills, plugins, MCP servers, auto memory, and CLAUDE.md so scripted calls start faster." Tool access drops to Bash, Read, Edit only. | `code.claude.com/docs/en/cli-reference`, `code.claude.com/docs/en/headless` |

None of these is a per-hook-entry toggle. `--disable-slash-commands`, `--safe-mode`, and `--bare` are all coarser than single-component ablation needs — each kills the entire class (or everything). `skillOverrides` and `disable-model-invocation` are the only mechanisms precise enough to toggle exactly one named skill without touching anything else. `--disable-slash-commands`'s exact scope — whether it also disables user-authored personal skills, not just bundled ones — is **UNVERIFIED**; the cli-reference page's own text for that flag doesn't distinguish, and I found no page that does.

## 4. How does the ablation skill's `tier3-arms.workflow.js` isolate arms today?

Read directly: `C:/Users/billy/.claude/skills/ablation/scripts/tier3-arms.workflow.js`.

It does not run real Claude Code sessions at all. The "Arms" phase calls the Workflow tool's `agent()` primitive twice per probe×rep — once for `steeringWith` (the full `steering` string as given), once for `steeringWithout` (the same string with the `component` substring removed via `A.steering.replace(A.component, '')`, whitespace-collapsed). Each call's prompt is literally:

```
SYSTEM CONTEXT (follow as standing instructions):
<steeringWith or steeringWithout>

TASK:
<probe>
```

This is prompt-text surgery on a subagent invocation, not configuration-file manipulation, and not a real `claude -p`/`claude` process. The "component" under test must be a literal substring of `steering` that a model can read and comply with — the script's frame-validation checks enforce this indirectly — the component string must occur exactly once in `steering`, and neither probe nor grading criterion may quote the component — but they never touch a settings file, a rules directory, or a skill loader.

What this means for each component class:

- **Rules file (`~/.claude/rules/*.md`)** — works with the mechanism as-is, no extension needed. A rules file's effect on behavior is entirely mediated by the model reading its prose in context; feeding the rule's text (or its absence) into `steering` reproduces that faithfully. This is mechanically identical to what the skill already validated on itself: `VALIDATION.md` records a self-ablation run where the component under test was the ablation skill's own `SKILL.md` prose, run through this exact template, producing a real CEREMONY verdict (the taxonomy's label for "no measurable effect", as distinct from load-bearing or harmful).
- **Skill — content ablation** ("does the skill's body still matter once loaded") — also works as-is, for the same reason: once a skill is invoked, its body is just prose in context, same as a rule or CLAUDE.md line. This is the case the self-ablation run already exercised.
- **Skill — discovery/triggering ablation** ("does removing the skill lose behavior because Claude no longer knows to reach for it") — NOT covered. The generic `agent()` subagent used by the template has no Skill tool, no skill listing, and no `/name` slash-command expansion to compete against. Testing whether a skill gets *found* under its real description-matching logic requires a session with the real skill-discovery machinery, which this template doesn't invoke.
- **Hook (PreToolUse or any lifecycle event)** — structurally NOT reproducible by this mechanism, and not fixable by adjusting args. A hook's effect is enforced by the Claude Code harness intercepting a tool call (per `code.claude.com/docs/en/hooks`, hooks "execute as shell commands at fixed lifecycle events and apply regardless of what Claude decides to do" — quoted from `code.claude.com/docs/en/memory`'s troubleshooting section, which draws exactly this hooks-vs-prose distinction: "Settings rules are enforced by the client regardless of what Claude decides to do. CLAUDE.md instructions shape Claude's behavior but are not a hard enforcement layer."). A generic subagent has no hook-execution pipeline at all; there is no "steering text" whose presence or absence can stand in for a hook, because a hook's behavior was never mediated by the model reading a description of it in the first place. Carrying hook components through this template would require a different Arms-phase implementation that shells out to real `claude -p` child processes (one per arm, per rep) against prepared `CLAUDE_CONFIG_DIR` directories — a different execution substrate than the current `agent()` calls, not an argument change. Whether the Workflow-tool runtime that executes `tier3-arms.workflow.js` can spawn subprocesses at all is **UNVERIFIED** from docs read for this task; that capability question would need to be resolved (or worked around by having a wrapper agent shell out via Bash and paste results back) before hook ablation could reuse this template's Grade/tally machinery.

## 5. Recommended recipe per component class

General setup for all three: run probes as headless `claude -p "<probe>" --output-format json` (or `stream-json`) calls with `CLAUDE_CONFIG_DIR` pointed at a **prepared, throwaway directory** built as a full copy of a minimal `~/.claude` tree, so neither arm ever touches the real interactive `~/.claude`. Pair with `--setting-sources user,project` (dropping `local`, or narrowing further to `user` alone) to guarantee no stray `.claude/settings.local.json` in whatever working directory the probe runs from contaminates either arm. Verify what actually loaded per arm using `/context`-equivalent evidence in headless mode: the `system/init` stream event reports loaded plugins and MCP servers per `code.claude.com/docs/en/headless`, and `code.claude.com/docs/en/memory` documents an `InstructionsLoaded` hook specifically "to log exactly which instruction files are loaded, when they load, and why" — wiring that hook into the prepared control-arm directory (only) gives a manipulation check that the intended component actually loaded, cheaply.

### Hook (user-level PreToolUse)

- **Control arm**: `CLAUDE_CONFIG_DIR=<arm-dir>/control claude --setting-sources user -p "<probe>"`, where `<arm-dir>/control/settings.json` contains the hook entry under test.
- **Ablated arm**: identical directory tree, `<arm-dir>/ablated/settings.json` byte-identical except the one hook entry is removed from the `hooks` object.
- **Why not `--settings`/`disableAllHooks`**: `--settings` merge-vs-replace semantics for the `hooks` key are unverified (§2); `disableAllHooks` and `allowManagedHooksOnly` are both all-hooks, not one. `CLAUDE_CONFIG_DIR` sidesteps the ambiguity entirely because there is no separate "user scope" `settings.json` left to merge against — the prepared directory *is* the user scope for that run.
- **Known confound**: if the same hook (or a functionally equivalent one) is also shipped by a plugin, it stays active in both arms regardless of what the arm directory's `settings.json` says. Primary source: "If the same handler is defined in multiple settings files, it runs once. However, plugin copies stay separate." (`code.claude.com/docs/en/hooks`.) Since a plugin's hook can't be deduplicated away by editing user settings, either disable the relevant plugin in the arm directories (a plugin's enablement is itself part of `~/.claude`'s config surface, so it moves with `CLAUDE_CONFIG_DIR`) or confirm via the manipulation check above that only one copy of the hook fired.
- **Constant, not a confound**: managed-policy hooks (§1) fire identically in both arms on the same machine; they don't need to be neutralized, only left alone.

### Rule (`~/.claude/rules/*.md`)

- **Sharper option**: `--settings '{"claudeMdExcludes":["<absolute-path-to-the-one-rule-file>"]}'` on the ablated arm only, default settings on the control arm. No file-tree duplication needed. Caveat: this specific use (excluding a *user*-scope rule, not a project one) is inferred from the general mechanism, not demonstrated in docs with a user-scope example (§2) — confirm with the manipulation check before trusting it for a real verdict.
- **Fallback with equal rigor**: same `CLAUDE_CONFIG_DIR` two-directory recipe as hooks, with the one rule file present/absent under `<arm-dir>/*/rules/`. This is unambiguous because it doesn't depend on the unverified `claudeMdExcludes`-on-user-scope inference.
- **Also valid, and cheaper than either**: since a rules file (unlike a hook) is pure model-facing prose, the *existing* `tier3-arms.workflow.js` mechanism (§4) already handles this correctly today, with no extension — pass the rule's full text as `component` and the surrounding rules-context as `steering`. This gets you the double-blind-graded, mechanically-tallied verdict machinery the hook/skill-discovery cases don't have yet, at the cost of testing "does this prose still change behavior when present in context" rather than "does this exact file, loaded through the real rules-loading path, still change behavior" — the two should coincide for a `paths`-unscoped rule loaded unconditionally, but would diverge for a path-scoped rule whose *triggering* (which files make it load) is itself part of what's under test.
- **Known confound**: none specific to rules beyond the general managed-CLAUDE.md-always-loads point (§1) and the general workspace-trust caveat — `autoMemoryDirectory` and similar project-scoped values are "honored only after you accept the workspace trust dialog for that folder" (`code.claude.com/docs/en/memory`); if probes run inside a real trusted-or-not project directory this can silently gate project-level (not user-level) inputs and should be neutralized by running probes from a fresh, already-trusted or trust-irrelevant working directory.

### Skill

- **Content ablation** (does the skill's body still earn its place once loaded): use the *existing* `tier3-arms.workflow.js` unmodified, exactly as validated in `VALIDATION.md`'s self-ablation run — pass the skill's body (or the paragraph under test) as `component`/`steering`. No extension needed; this is the one case the tool already does well.
- **Discovery ablation** (does removing the skill lose behavior because Claude stops reaching for it): needs real sessions, not `agent()` calls. **Control arm**: default `CLAUDE_CONFIG_DIR` arm directory with the skill present under `<arm-dir>/skills/<name>/`. **Ablated arm**: same directory tree, `--settings '{"skillOverrides":{"<name>":"off"}}'`, which per `code.claude.com/docs/en/skills` hides the skill's name and description from Claude entirely (not just from the `/` menu) — a cleaner ablation than deleting the directory, because it's a single-flag diff between otherwise-identical arm invocations and doesn't require two directory trees at all for this component class.
- **Known confound**: plugin skills are namespaced (`plugin-name:skill-name`) and, per `code.claude.com/docs/en/skills`, "cannot conflict with other levels" — meaning they also don't get deduplicated against a same-purpose personal skill. If a plugin under test ships a skill that duplicates the personal skill's function under a different name, ablating the personal copy via `skillOverrides` leaves the plugin's copy fully invocable, and the ablated arm will silently fail to isolate anything. Also note `skillOverrides` explicitly does not affect plugin skills at all ("Plugin skills are not affected by `skillOverrides`. Manage those through `/plugin` instead.") — so if the component under test is itself a plugin-provided skill, `skillOverrides` is the wrong tool; use `--plugin-dir`-based enablement control or the `CLAUDE_CONFIG_DIR` directory-swap instead.

## Summary answer to the sharpest-mechanism question

`CLAUDE_CONFIG_DIR` pointed at a pair of prepared, otherwise-identical directory trees is the one mechanism that isolates all three component classes (hook, rule, skill) uniformly and unambiguously, because it relocates the entire user-scope config surface rather than trying to override or merge individual keys whose per-key semantics are, for hooks specifically, unverified. `--setting-sources user` (or `user,project` when project context is needed) should be paired with it to rule out `local`/`project`-scope contamination from wherever the probe happens to run. Two lighter-weight, single-flag alternatives exist and are precise enough to trust once independently verified: `skillOverrides` for a single personal/project skill, and (with lower confidence, unverified on user scope) `claudeMdExcludes` for a single rule file. Neither has a hook-specific analogue, which is why hooks specifically should default to the `CLAUDE_CONFIG_DIR` directory-swap recipe rather than any `--settings`-key approach.

The existing `tier3-arms.workflow.js` needs no changes to ablate rules-file prose or a skill's body content — both are pure model-facing text, exactly the shape the template already handles via literal-substring removal from `steering`. It structurally cannot ablate a hook's real behavior (hooks are harness-enforced, not model-comprehension-mediated) or a skill's discovery/triggering behavior (the generic subagent has no Skill tool or skill listing to compete against), and extending it to either would mean adding a second Arms-phase code path that spawns real `claude -p` processes against prepared `CLAUDE_CONFIG_DIR` directories in place of the current `agent()` calls — a different execution substrate, not a new argument.
